## 0. Verdict at a glance

1. **Keep the script and make it work.** Add a flat `eslint.config.js` with `@eslint/js` recommended,
   `typescript-eslint` recommended (not type-checked), and `react-hooks` (`rules-of-hooks` + `exhaustive-deps`).
2. **The tree is nearly clean: 8 problems, all fixed in this ticket, nothing baselined.** Measured with the exact

   (exit 0).
3. **`exhaustive-deps` has 0 hits.** The three intentional dependency omissions already have disable comments
   (`KitPlayer.tsx:235`, `web.tsx:141`, `vega.tsx:53`). They were written for this plugin. Turn the rule on as an
   **error**: the kit depends on effect ordering, so any new omission must carry a visible disable comment.
4. **Add `pnpm lint` to CI** (a `test` job step after `typecheck`). It takes seconds. The script broke because nothing
   ever ran it.

- History: the scaffold (`de646a1`) added `"lint": "eslint src test"` and `eslint@^9` but no config, and no plugins. No
  `eslint.config.*` or `.eslintrc*` has ever been in the repo (`git log --all -- '.eslintrc*' 'eslint.config.*'` is
  empty). So lint has never run. CI (`.github/workflows/ci.yml`) runs typecheck/test/build and the harness, but not lint.
- The source already contains disable comments that expect a config: `no-console` (log.ts ×2, contentLauncher.ts ×1),
  `@typescript-eslint/no-var-requires` (rnv.ts ×1, w3c.ts ×2) and `react-hooks/exhaustive-deps` (×3).
- **"Crashed inside ESLint": not reproduced.** Every run on `efefa95` gives the missing-config error above (exit 2). The
  most likely cause is a run from a worktree that had a partial or stray config, or one without `node_modules`. Any
  config that names `react-hooks/*` or `@typescript-eslint/*` rules without loading the plugin makes ESLint 9 abort with
  "Could not find plugin" or "Definition for rule … was not found". That is how the existing disable comments would
  crash a bare config. The config below loads both plugins, so that failure cannot occur. Not blocking.
- ORCHESTRATOR §3's `pnpm lint:words` is an **app** script (the wording rules in the consuming apps). It is unrelated
  to this repo's `lint` and is out of scope.

## 3. Exact config — `eslint.config.js`

```js
// Flat config (ESLint 9). Library lint: correctness rules only, no style rules (formatting is not enforced here).
import js from '@eslint/js'
import tseslint from 'typescript-eslint'
import reactHooks from 'eslint-plugin-react-hooks'

export default tseslint.config(
  { ignores: ['dist/**', 'node_modules/**', 'harness/**', 'examples/**', 'coverage/**'] },
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    files: ['**/*.{ts,tsx}'],
    plugins: { 'react-hooks': reactHooks },
    rules: {
      'react-hooks/rules-of-hooks': 'error',
      // The kit depends on effect ordering. Each deliberate omission needs a disable comment with a reason.
      'react-hooks/exhaustive-deps': 'error',
      // The library logs only through src/platform/log.ts and the documented warn-once sites.
      'no-console': 'error',
      '@typescript-eslint/no-unused-vars': [
        'error',
        { argsIgnorePattern: '^_', varsIgnorePattern: '^_', caughtErrorsIgnorePattern: '^_' },
      ],
    },
  },
  {
    // Tests spy on console and use loose rigs for mocked native modules.
    files: ['test/**'],
    rules: { 'no-console': 'off', '@typescript-eslint/no-explicit-any': 'off' },
  },
  { linterOptions: { reportUnusedDisableDirectives: 'error' } },
)
```

Why this config:
- **Not type-checked** (`recommended`, not `recommendedTypeChecked`). It is fast, it needs no `parserOptions.project`,
  and `tsc --noEmit` already runs in CI. A type-aware lint can be its own ticket if someone wants it.
- **`no-console: error`** turns the three existing `// eslint-disable-next-line no-console` comments into meaningful
  guards. Without it they become "unused directive" errors. In `src`, no unguarded `console` call exists today.
- **`reportUnusedDisableDirectives: 'error'`** stops stale disable comments from building up. The current
  `no-var-requires` comments are exactly that kind of stale comment: the rule was renamed `no-require-imports` in
  typescript-eslint v8.
- `harness/` and `examples/` stay out of scope (the script is `eslint src test`; the ignores make a bare `eslint .`
  behave the same). Linting the harness is a possible follow-up (§9 Q2).

### The deliberate ref / effect patterns

All three intentional omissions are already annotated, and the rule reports **0 violations** on the current tree:
- `src/player/KitPlayer.tsx:235` — `}, [sourceUri]) // eslint-disable-line react-hooks/exhaustive-deps` (per-source reset)
- `src/player/adapters/web.tsx:141` — `}, [props.source.uri]) // eslint-disable-line …` (load effect keyed on uri)
- `src/player/adapters/vega.tsx:53` — `// eslint-disable-next-line …` (Shaka lifecycle)

Elsewhere the kit reads `xRef.current` inside effects and callbacks, which `exhaustive-deps` does not flag (refs are
stable). **Rule for future code** (put it in the config comment, as above): a deliberate omission gets a line-level
disable **plus a reason** in the adjacent comment. No file-level disables, and no downgrade to `warn`. Do not add
reason text to the three existing sites in this ticket. That is a churn-only change, and two of them already have
reasons in the surrounding comments.

## 6. The 8 violations under §3 (measured), and their fixes — all in this ticket

| # | Location | Rule | Fix |
|---|---|---|---|
| 1 | `src/core/vtt.ts:199` `.replace(/^<U+FEFF>/, '')` | `no-irregular-whitespace` | write `/^﻿/`. Same regex, now visible |
| 2 | `test/hls.test.ts:81` `` `<U+FEFF>${…}` `` | `no-irregular-whitespace` | write `` `﻿${…}` ``. Same string |
| 3–4 | `src/player/adapters/rnv.ts:13-14` | unused directive (`no-var-requires`) + `no-require-imports` | rename the disable to `@typescript-eslint/no-require-imports` |
| 5–8 | `src/player/adapters/w3c.ts:13-14, 17-18` | same, ×2 | same rename, ×2 |

The `require()` calls are deliberate: they lazily load optional peer dependencies, so the module does not crash when a
peer is absent. They stay as they are. Before the test override, `test/fireos-adapter.test.tsx:14` (`Record<string, any>` rig)
also hit `no-explicit-any`. The `test/**` override covers it, so no code change is needed.

Verified: with these edits applied to a scratch copy of `src` and `test`, the §3 config exits 0. The BOM edits keep the
same behaviour (an escape sequence names the same code point), and the existing VTT/HLS BOM tests cover them.

**No baseline file, no `--max-warnings` games.** Everything is `error`, so `eslint` exits non-zero on any problem.

## 9. Risks / open questions

**Risks**
- *ESLint 10 / `@eslint/js` 10 drift.* `@eslint/js` is now on 10.x. An unpinned `pnpm add -D @eslint/js` would install
  10 next to ESLint 9. The explicit `@^9.39.5` prevents this.
- *`tseslint.config()` helper deprecation.* Newer typescript-eslint releases recommend `defineConfig` from
  `eslint/config`. On ESLint 9.39 both work. If the implementer sees a deprecation warning, replace the wrapper with
  `import { defineConfig } from 'eslint/config'` (same array). This is not a blocker.
- *Workspace consumers.* None. The config is not shipped (`files` in package.json does not include it).

**Open questions (none blocking)**
- Q1. Move to `eslint-plugin-react-hooks@7` and adopt some React Compiler rules (`refs`, `set-state-in-effect`, …)?
  Those rules would probably flag the deliberate ref-in-render / ref-sync patterns that KIT-011/015/020 depend on. That
  needs a fable judgement and its own ticket. Not now.
- Q2. Lint `harness/` too (it has its own tsconfig)? Cheap follow-up. Leave out to keep this ticket minimal.
- Q3. Type-aware rules (`no-floating-promises` would be valuable around `void p.destroy()` / Shaka `load()`)? Separate
  ticket. It needs `parserOptions.projectService` and roughly doubles lint time.
